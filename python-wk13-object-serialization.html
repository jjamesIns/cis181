Object Serialization

You can build objects that hold data and protect it with their own methods. You can write text to a file and read it back. This module joins the two: how to save an entire object — attributes and all — to a file, and rebuild it later as a working object with its methods intact. Converting an object to bytes is serializing; rebuilding it is deserializing. Python calls the pair pickling and unpickling, and together they turn a program that forgets everything when it closes into one that remembers.

The problem

Why serialize?

Everything a program builds lives in RAM, and RAM is wiped the moment the program ends. In Week 07 you solved that for text: write the values to a file, read them back, convert them. That works — but look at what it costs when the data is an object.

Suppose an Aircraft object holds a tail number, a model, and an hours-flown total. Saving it as text means taking the object apart by hand, and loading it means putting it back together by hand:

the hard way.py
# saving — disassemble the object, field by field
out = open("fleet.txt", "w")
out.write(plane.get_tail() + "\n")
out.write(plane.get_model() + "\n")
out.write(str(plane.get_hours()) + "\n")   # don't forget str()
out.close()

# loading — reassemble it, in exactly the right order
inp = open("fleet.txt", "r")
tail = inp.readline().rstrip("\n")          # don't forget rstrip()
model = inp.readline().rstrip("\n")
hours = float(inp.readline())               # don't forget float()
inp.close()
plane = Aircraft(tail, model, hours)         # rebuild by hand

Three attributes, and already there are six places to make a mistake. Add a fourth attribute and you must edit both halves. Change the order in one half and the data loads into the wrong fields — silently.

Serializing does this for you

Serializing an object means converting it into a stream of bytes that can be written to a file. Deserializing is the reverse — reading those bytes back and rebuilding an equivalent object. Python's words for the two directions are pickling and unpickling. The whole exchange above collapses to two lines in each direction — and it never gets longer as the class grows.

You met pickling briefly in Week 10, applied to a dictionary. This module takes it further: pickling objects of the classes you write, several of them, and whole collections at once.

The two calls

dump and load

The pickle module has exactly two functions you need. Both take a file object — and both require that file to be opened in binary mode.

CallWhat it doesFile mode
pickle.dump(object, file)Serializes the object and writes the bytes to the file."wb"
pickle.load(file)Reads the next object's bytes and rebuilds it."rb"
round_trip.py
import pickle

# WRITE — note "wb", not "w"
out_file = open("data.dat", "wb")
pickle.dump(some_object, out_file)
out_file.close()

# READ — note "rb", not "r"
in_file = open("data.dat", "rb")
restored = pickle.load(in_file)
in_file.close()
Why the b

Every file mode you used in Week 07 — 'r', 'w', 'a' — opens the file in text mode, where Python encodes and decodes characters for you. Pickle does not produce characters; it produces raw bytes. Adding b tells Python to pass those bytes through untouched. A pickle file opened in a text editor looks like garbage, and that is expected.

The bytes themselves are not meant to be read by people. Here is what a small pickled object actually looks like on disk:

what's in the file
>>> open("data.dat", "rb").read()[:12]
b'\x80\x04\x95x\x00\x00\x00\x00\x00\x00\x00\x8c'
Warming up

Serializing a dictionary

Start with a container you already know. In Week 10 you pickled a dictionary; it is worth doing once more here, because everything that follows — including serializing your own objects — works exactly the same way.

save_dict.py
import pickle

logbook = {"call_sign": "BR-204",
           "hours": 312.5,
           "ratings": ["IFR", "night"]}

# SERIALIZE — object in, bytes out
out_file = open("logbook.dat", "wb")
pickle.dump(logbook, out_file)
out_file.close()

Deserializing gives back a real dictionary — not text that needs parsing, and not a flattened version. Everything nested inside it returns with its own type intact:

load_dict.py
import pickle

# DESERIALIZE — bytes in, object out
in_file = open("logbook.dat", "rb")
logbook = pickle.load(in_file)
in_file.close()

print(logbook["call_sign"])        # BR-204
print(logbook["hours"] + 10)      # 322.5  ← a float, not a string
print(logbook["ratings"][0])      # IFR    ← still a list inside
Compare this to Week 07

Written as text, 312.5 would come back as the string '312.5\n' and need rstrip and float before you could add to it. The nested list would be worse — you would have to invent a way to store several values on one line and split them apart again. Pickle restores the types, not just the characters.

Nesting can go as deep as you like. A dictionary holding a set, a list, and another dictionary comes back whole:

nested.py
flight = {"crew": {"Ana", "Dev"},                  # a set
          "legs": [{"from": "SNA", "to": "LAS"}],  # a list of dicts
          "count": 2}

# after a dump/load round trip:
print(type(flight["crew"]))       # <class 'set'>  ← still a set
print(flight["legs"][0]["to"])   # LAS           ← inner dict intact
One habit to notice

Deserializing builds a new object. If you compare the restored dictionary to the original with == the answer is True — the values match — but is returns False, because it is a separate object rebuilt from the file. That distinction matters more once you are restoring objects of your own classes.

The main event

Serializing your own objects

That is the warm-up. The real payoff is serializing instances of the classes you write — and the good news is that dump and load do not change at all. Here is a class of the kind you built in Week 12 — private attributes, accessors, a mutator, and a __str__:

aircraft.py
class Aircraft:
    def __init__(self, tail, model, hours):
        self.__tail = tail
        self.__model = model
        self.__hours = hours

    def add_hours(self, amount):
        self.__hours = self.__hours + amount

    def get_tail(self):
        return self.__tail

    def get_hours(self):
        return self.__hours

    def __str__(self):
        return f"{self.__tail} ({self.__model}) — {self.__hours} hrs"

Pickling one is no different from pickling a dictionary — dump does not care what kind of object it receives:

save_one.py
import pickle

plane = Aircraft("N412SP", "Cessna 172", 1840.5)

out_file = open("fleet.dat", "wb")
pickle.dump(plane, out_file)
out_file.close()

Now the important part. What comes back from load is not a dictionary of values you must reassemble — it is a working Aircraft:

load_one.py
import pickle

in_file = open("fleet.dat", "rb")
plane = pickle.load(in_file)
in_file.close()

print(type(plane))          # <class '__main__.Aircraft'>
print(plane)                # N412SP (Cessna 172) — 1840.5 hrs  ← __str__ works
plane.add_hours(10.5)       # ← its mutator works too
print(plane.get_hours())    # 1851.0
Private attributes survive

__tail, __model, and __hours are all private, yet they came back intact. Pickle stores an object's attributes regardless of privacy — the underscores control access from other code, not what the object itself contains. You still read them the same way you always did: through the accessors.

Equivalent, not identical

Unpickling builds a new object with the same state. If you pickle plane and immediately load it back into copy, then copy is plane is False — they are two separate objects that happen to hold equal values. That is exactly what you want from something reconstructed from a file.

More than one

Many objects, one file

You can call dump repeatedly on the same open file. Each call appends another object's bytes, and load retrieves them in the same order, one call per object.

save_many.py
import pickle

fleet = [Aircraft("N412SP", "Cessna 172", 1840.5),
         Aircraft("N78KL", "Piper Archer", 932.0),
         Aircraft("N221RV", "Cirrus SR20", 405.25)]

out_file = open("many.dat", "wb")
for plane in fleet:
    pickle.dump(plane, out_file)   # one dump per object
out_file.close()

Reading them back raises a question you have faced before: how do you know when to stop? A text file signals end-of-file with an empty string. Pickle does something different — load raises an EOFError when there is nothing left. That makes the reading loop a try/except:

load_many.py
import pickle

fleet = []
in_file = open("many.dat", "rb")
try:
    while True:                       # keep going until the file runs out
        fleet.append(pickle.load(in_file))
except EOFError:
    pass                              # normal ending, not a bug
finally:
    in_file.close()                  # closes on every path

for plane in fleet:
    print(plane)
# N412SP (Cessna 172) — 1840.5 hrs
# N78KL (Piper Archer) — 932.0 hrs
# N221RV (Cirrus SR20) — 405.25 hrs
An exception used as a sentinel

This is the one place where catching an exception is the normal path rather than error handling. EOFError here means "you have read everything," which is a success, not a failure — so the handler does nothing but pass. Note the finally: it guarantees the file closes whether the loop ended cleanly or something else went wrong.

The simpler way

Pickling a whole collection

There is a shortcut that avoids the EOFError loop entirely. Pickle can serialize a container — a list, a dictionary, a set — and it serializes everything inside it, including your own objects, however deeply nested.

whole_list.py
import pickle

# SAVE the entire list in ONE dump
out_file = open("fleet_list.dat", "wb")
pickle.dump(fleet, out_file)      # fleet is a list of Aircraft objects
out_file.close()

# LOAD it back in ONE load — no loop, no EOFError
in_file = open("fleet_list.dat", "rb")
fleet = pickle.load(in_file)
in_file.close()

print(len(fleet))            # 3
print(fleet[0])             # N412SP (Cessna 172) — 1840.5 hrs
print(type(fleet[0]))       # <class '__main__.Aircraft'>  ← still an object

A dictionary of objects works the same way, which is often the most useful shape — a lookup that survives between runs:

dict_of_objects.py
by_tail = {"N412SP": plane_a, "N78KL": plane_b}

out_file = open("hangar.dat", "wb")
pickle.dump(by_tail, out_file)
out_file.close()
# later: by_tail = pickle.load(in_file) → keys AND Aircraft values, intact
ApproachUse it when…
One dump per objectObjects are produced over time and appended as you go, or the file may be huge and you want them one at a time.
One dump of the whole collectionYou have all the objects at once. Simpler code, no EOFError loop — the usual choice.
Debugging

What goes wrong

Four mistakes account for nearly every pickling problem. Each raises a different exception, so the message tells you which one you made.

1Forgetting the b in the file mode▸

Opening with "w" instead of "wb" raises TypeError: write() argument must be str, not bytes — pickle handed the file bytes, and a text-mode file only accepts strings.

Reading with "r" instead of "rb" gives a UnicodeDecodeError, because Python tries to interpret the raw bytes as characters and the very first byte is not valid text.

2The file does not exist▸

FileNotFoundError, exactly as in Week 07 — and handled the same way. A program that loads saved data at startup should expect this on its very first run, when no file has been written yet, and start with empty data instead of crashing.

3Loading from an empty or exhausted file▸

EOFError: Ran out of input. Expected when a reading loop finishes — but if it happens on the first load, the file is empty, which usually means an earlier dump never ran or the file was never closed.

4The class is not defined when you load▸

This is the one that surprises people. A pickle file does not contain the class — it stores the object's data plus the class's name. Loading it in a program that has never defined Aircraft raises:

AttributeError: Can't get attribute 'Aircraft' on <module '__main__'>

The fix: the class definition must be available wherever you unpickle — normally by keeping the class in its own module and importing it in both programs.

A safe startup pattern

Combine two of these into the pattern most programs use — try to load saved data, and fall back to empty if there is none yet:

safe_startup.py
try:
    in_file = open("fleet_list.dat", "rb")
    fleet = pickle.load(in_file)
    in_file.close()
except (FileNotFoundError, EOFError):
    fleet = []                # first run — nothing saved yet
Judgment

Trust and portability

Pickle is convenient, and that convenience has two limits worth knowing before you reach for it in real work.

Never unpickle data you do not trust

Unpickling can execute code contained in the file. A malicious pickle file can run anything the program's user can run. Treat a pickle file the way you would treat a program someone emailed you: load it only if you created it or it came from a source you fully trust. Never unpickle something uploaded by a user or downloaded from the open internet.

The second limit is portability. A pickle file is Python-specific — a Java or JavaScript program cannot read it, and it depends on your class definitions staying compatible. When data has to cross language boundaries or be read by people, a text format such as JSON or CSV is the better choice, at the cost of writing the conversion yourself.

PickleText / JSON
Handles your own objectsYes, automaticallyNot directly — you convert by hand
Human-readableNo, binaryYes
Readable by other languagesNoYes
Safe with untrusted filesNoYes
The rule of thumb

Pickle is excellent for a program saving its own state to reload later — a saved game, a cached fleet list, a program's settings. It is the wrong tool for exchanging data with other systems or accepting files from strangers.

Self-test

Check yourself

Q1What does it mean to serialize an object, and what is Python's word for it?▸

Converting the object into a stream of bytes that can be written to a file and later read back and rebuilt into an equivalent object. Python calls it pickling; the reverse is unpickling.

Q2What is the difference between serializing a dictionary and serializing an object of your own class?▸

From your side, nothing — both are one pickle.dump call and one pickle.load. The difference is on the way back: a dictionary returns as a dictionary, while your object returns as a full instance with its methods available. The one extra requirement for your own classes is that the class must be defined in the program doing the loading.

Q3Which two file modes does pickle require, and why?▸

"wb" to write and "rb" to read. The b means binary: pickle produces raw bytes rather than characters, so the file must not be opened in text mode.

Q4After unpickling an Aircraft, can you call its methods?▸

Yes. What comes back is a full Aircraft object, not a bag of values — its accessors, mutators, and __str__ all work. Its private attributes come back intact too.

Q5How do you know when you have read the last object from a file of many?▸

pickle.load raises EOFError. Wrap the reading loop in a try/except EOFError, where the handler simply ends the loop — here the exception is the normal ending, not an error.

Q6How can you avoid the EOFError loop altogether?▸

Put the objects in a list (or dictionary) and pickle the collection in a single dump. One load brings the whole thing back, objects included.

Q7Why might a load fail with AttributeError: Can't get attribute 'Aircraft'?▸

The pickle file stores the object's data and the class's name, not the class itself. The program doing the loading must have the Aircraft class defined or imported, or Python cannot rebuild the object.

Q8Name one situation where pickle is the wrong choice.▸

Any file coming from an untrusted source, since unpickling can execute code — or any data that must be read by a non-Python program or by a person, where JSON or CSV is appropriate instead.

Reference

Key terms

serialize
To convert an object into a stream of bytes that can be saved and later rebuilt.
pickling
Python's name for serializing an object, done with pickle.dump.
deserialize
To rebuild an object from its serialized bytes; the reverse of serializing.
unpickling
Rebuilding an object from its serialized bytes, done with pickle.load.
binary mode
A file mode — "wb" or "rb" — that reads and writes raw bytes instead of text.
EOFError
The exception pickle.load raises when no objects remain in the file.
pickle file
A binary file holding one or more serialized objects; not human-readable.
