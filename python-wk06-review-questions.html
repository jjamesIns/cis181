True or False

11 × 1 pt = 11
  1. T / F

    A traceback should be read from the bottom up, because the last line names the exception type.

  2. T / F

    Statements written after a raise statement in the same block will still execute before the function ends.

  3. T / F

    The function that raises an exception is usually the best place to decide how the program should recover from it.

  4. T / F

    A custom exception class must define at least one method to be usable.

  5. T / F

    A custom exception that inherits from Exception can still be caught by a general except Exception clause.

  6. T / F

    Every unusual outcome a function encounters should be reported by raising an exception.

  7. T / F

    An except clause runs only when the type of exception it names is raised in the try suite.

  8. T / F

    The same function can be reused in several programs, each handling its exceptions differently.

  9. T / F

    Placing a catch-all except: before a more specific except ValueError: causes a syntax error.

  10. T / F

    An except ValueError clause can only catch exceptions the programmer raised explicitly with raise.

  11. T / F

    Raising Exception("error") gives the caller as much useful information as raising a specific type with a descriptive message.

Short Answer · 2 points each

  1. Detection vs. handling.The function knows the rules of its own job, so it is the right place to notice that an argument is out of range or otherwise impossible — it detects. The caller has the surrounding context — whether to re-ask the user, substitute a default, log the problem, or give up — so it decides the response. Separating them means the same function can be reused in many programs, each recovering in the way that suits it.
  2. The two pieces of a raise.An exception type and a message. The type lets callers catch exactly the failure they expect with a matching except; the message explains what went wrong to whoever reads the traceback.
  3. Why raise instead of returning a default.A returned default may go unnoticed, and the bad value then flows downstream and causes a confusing failure far from its real cause. Raising stops the problem at its source and forces the caller to deal with it deliberately.
  4. Rule of thumb.Raise for the exceptional, return for the normal. Test: "Is this a result the caller might reasonably expect on a good day?" A search that finds nothing is normal — return None or an empty list. A temperature below absolute zero means the function cannot do its job at all — raise.
  5. Three good reasons to raise.Invalid arguments (out of range, empty when it must not be, wrong type — a violated precondition); an impossible request (withdrawing more than the balance, averaging an empty list); and a broken assumption, where something the function relied on turned out to be untrue so continuing would produce nonsense.
  6. ValueError vs. TypeError.ValueError is for an argument of the right type but an unacceptable value — a percentage of 150, or an empty string where text is required. TypeError is for an argument of the wrong type entirely — a string or a list passed where a number is required.
  7. A good message.It is written for the person who will read the traceback — usually a programmer debugging the failure. It states what was expected and, where useful, what was actually received, so the reader can identify the problem without reading the function's source.
  8. Why raise Exception("error") is poor.It tells the caller almost nothing about what failed, and because it is the most general type it can only be caught by a broad except Exception — which also swallows unrelated bugs the programmer never intended to catch, hiding real defects.
  9. Custom exception types.Write a class that inherits from Exception; an empty body with pass is enough. Two reasons from: the name documents precisely what category of failure occurred; callers can catch that exact problem without also catching every other ValueError; and because it is a class it can carry extra attributes, such as the offending value, for the handler to use.
  10. Propagation.The exception travels up the call chain to the function's caller, and onward to that function's caller, until some try / except catches it. If nothing anywhere handles it, the program halts and displays a traceback.
  11. as, else, and finally.as err captures the exception object so the handler can read its message. else runs only when the try suite raised nothing. finally runs every time, whether or not an exception occurred, and is used for cleanup.

Algorithm Workbench · 1 point each

  1. Single raise.raise ValueError("age cannot be negative")
  2. set_age.def set_age(age): with if age < 0: raise ValueError("age cannot be negative") then return age.
  3. withdraw.Two guard clauses before the return: if amount <= 0: raise ValueError("amount must be positive") and if amount > balance: raise ValueError("insufficient funds"), then return balance - amount.
  4. Choosing types.a. ValueError · b. TypeError · c. KeyError · d. IndexError · e. ZeroDivisionError
  5. try / except for to_kelvin.try: / kelvin = to_kelvin(reading) / print("Converted:", kelvin) / except ValueError as err: / print("Could not convert:", err)
  6. Custom exception.class InsufficientFundsError(Exception): pass
  7. Using the custom type.Change the second guard to raise InsufficientFundsError("insufficient funds"). Advantage: the caller can write except InsufficientFundsError to offer an overdraft or a transfer, while a separate except ValueError still catches the invalid-amount case — two different failures now get two different responses.
  8. Trace 1.One line: caught: negative. Neither "checked" nor "after call" prints — the raise ends the function immediately, and the exception skips the rest of the try suite.
  9. Trace 2.Three lines, in order: process · validate · handled. Neither "after validate" nor "after process" prints, because the exception propagates out of both functions to the try.
  10. Trace 3.demo(1) prints try-ok, else, finally. demo(-1) prints except, finally. Note else is skipped when an exception occurs, and finally runs both times.
  11. Ordering bug.The catch-all except: appears before a specific clause, which Python rejects with SyntaxError: default 'except:' must be last. Fix by moving except ValueError: above the bare except: — or better, delete the bare clause entirely.
  12. set_quantity.if not isinstance(n, int): raise TypeError("quantity must be an int, got " + type(n).__name__) then if n < 0: raise ValueError("quantity cannot be negative: " + str(n)) then return n.
  13. average.def average(numbers): with if len(numbers) == 0: raise ValueError("cannot average an empty list") then return sum(numbers) / len(numbers). The guard is what prevents a ZeroDivisionError.
  14. Robust loop.rating = None, then while rating is None: containing a try that assigns rating = get_rating(input("Rate 1-5: ")) and an except ValueError as err: that prints err.
  15. Raise or return?Return — most reasonably None. A customer who does not exist yet is a result the caller might expect on a good day, and the caller checks for it every time, so it is normal rather than exceptional. Reserve the exception for cases where the function truly cannot do its job.
  16. Why the specific message.It states both what was expected (an int) and what actually arrived (a str), so a programmer reading the traceback can identify the defect without opening the function's source. "bad input" says only that something failed, leaving the reader to reconstruct which argument and why.

  1. Step 2 — reading the traceback.The last line carries both: the exception type before the colon (ValueError) and the programmer's message after it. The lines above it are the call stack, showing which line of which function raised. Students often read only the first line; point out that the useful information is at the bottom.
  2. Step 3 — what err is.err is the exception object itself, captured by as. Printing it displays the message text that was passed to ValueError(...) inside the function — so the text travels from the raise site to the handler as part of the object.
  3. Step 4 — code after the raise.It does not print. raise ends the function immediately; no statement after it in that path is ever reached. This is why guard clauses can be written at the top of a function without an else.
  4. Step 5 — why silent failure is worse.Returning 0 produces a number that looks legitimate, so result * 2 computes 0 and the program carries on with meaningless data. The eventual symptom — a wrong report, a bad average — appears far from the actual cause, and the printed warning may scroll past unread. A crash is loud and points directly at the source; a wrong answer is silent and points nowhere.
  5. Step 7 — why prefer the specific catch.except TemperatureError responds only to this failure and lets every other error propagate, so genuine bugs still surface. except Exception also swallows unrelated problems — a typo'd variable name, a failed conversion — and hides them behind a temperature-related message.

Exercise 2 · The Unbreakable Rating Prompt — 10 points

...         rating = get_rating(input("Rate 1-5: "))

...         print("Try again (", err, ")")
...

  1. Step 2 — where the second ValueError came from. Only "9" triggered the raise the student wrote. "abc" failed one line earlier, inside int(), which raises its own ValueError with the message invalid literal for int() with base 10: 'abc'. This is the important insight of the exercise: a single except ValueError catches both — errors raised by built-in functions and errors raised deliberately — because they are the same type. Full credit requires naming int() as the source.
  2. Step 5 — why rating stays None.When get_rating raises, the assignment never completes — the right side must produce a value before anything is stored — so rating keeps its previous value of None and the loop condition remains true. If the assignment sat outside the try, the exception would not be caught at all: it would propagate out of the loop and halt the program, which is precisely the crash the design exists to prevent.
  3. Step 6 — which clauses ran.On the bad entry: the try suite raised, so except ran, else was skipped, and finally ran — output is the error message followed by attempt finished. On the good entry: the try suite succeeded, so except was skipped, else ran, and finally ran — output is accepted followed by attempt finished. finally runs on every attempt regardless.
  4. Step 7 — detection vs. response.get_rating performs the detection: it knows the rule that a rating must be 1 through 5 and raises when that rule is broken. The loop in the calling code performs the response: it decides that the right recovery is to show a message and ask again. Because the function does not print anything itself, the same function could be reused in a web form that displays the message beside a field, in a batch script that logs it and skips the record, or in a test that asserts the exception was raised — each caller chooses its own recovery without modifying the function.
