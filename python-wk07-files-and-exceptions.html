Files and Exceptions

Until now, every value a program produced vanished the moment it stopped. Files let your data outlive a single run — saved to disk, read back later. And because the outside world is messy, you'll also learn to catch the errors that file work tends to raise.

Foundation

Why programs use files

The variables you've used so far live in RAM, which is wiped clean every time a program ends. For data to survive between runs — a saved game, a customer list, last month's readings — it has to be written to a file, usually on a disk.

Two directions, two names for the file:

  • Writing data to a file means saving data onto it. A file your program writes to is an output file.
  • Reading data from a file means retrieving data that's already there. A file your program reads from is an input file.

Whichever direction you go, working with a file always takes the same three steps:

1 · 2 · 3Open, process, close▸
  • Open the file — connect your program to it and say whether you intend to read or write.
  • Process the file — write data to it, or read data from it.
  • Close the file — disconnect, which flushes any pending writes and frees the file for other programs.
Categories

File types and access methods

Files come in two broad types, and there are two ways to reach the data inside them.

Two types of files

  • A text file contains data encoded as text — readable characters you could open in a plain editor. This module works exclusively with text files.
  • A binary file contains data that has not been converted to text, stored in the computer's raw internal format (images and compiled programs, for example).

Two ways to access data

  • Sequential access reads a file straight through from beginning to end, like a cassette tape — you can't skip ahead. Everything in this module uses sequential access.
  • Direct access (also called random access) lets you jump straight to any piece of data in the file, in any order.

Filenames and file objects

A filename extension is the short sequence of characters after the final period in a name — .txt, .csv, .dat — and it hints at what kind of data the file holds. When your program opens a file, Python gives you a file object: an object that represents that specific file and provides the methods you use to work with it. You keep the file object in a variable.

Step one

Opening a file

The built-in open function connects your program to a file. It creates a file object tied to a file on disk and returns it, which you store in a variable.

open_format.py
file_object = open(filename, mode)

The mode is a short string telling Python how you plan to use the file. The three you'll use most:

ModeMeaningIf the file already exists
'r'Open for reading only.Opens it. (Error if it doesn't exist.)
'w'Open for writing.Erases it and starts fresh. Creates it if absent.
'a'Open for appending.Keeps it; new data is added at the end. Creates it if absent.
opening.py
# open weather.txt for writing
outfile = open("weather.txt", "w")

# later, open the same file for reading
infile = open("weather.txt", "r")
Where the file lives

If you give open just a filename with no folder path, Python looks in the same directory as the program — and creates new files there too. To use a full path on Windows, prefix the string with r so the backslashes aren't treated as escape characters: open(r"C:\\data\\weather.txt", "r").

Step two, outbound

Writing data to a file

A method is a function that belongs to an object and operates on it. To write to a file, you call the file object's write method, passing the string to store. When you're done, you call its close method.

write_cities.py
outfile = open("cities.txt", "w")

outfile.write("Tokyo\n")
outfile.write("Cairo\n")
outfile.write("Lima\n")

outfile.close()
The newline matters

The write method does not add line breaks for you. To store separate items on separate lines, concatenate a newline character '\n' onto each piece of data — usually with the + operator inside the write call, like outfile.write(city + '\n'). Without it, everything runs together on one line.

Appending versus overwriting

Opening a file in 'w' mode erases any existing contents the moment it opens — useful when you want a clean file, dangerous when you didn't. To add to a file instead, open it in 'a' mode: existing data is preserved and new writes land at the end. (If the file doesn't exist yet, 'a' creates it.)

append.py
# add a city without erasing the three already there
outfile = open("cities.txt", "a")
outfile.write("Oslo\n")
outfile.close()
Step two, inbound

Reading data from a file

Once a file is open for reading, two methods pull data out of it. Both return what they read as a string.

  • The read method reads the entire file contents into memory as one string.
  • The readline method reads a single line, returning it as a string that still includes the trailing '\n'.
read_all.py
infile = open("cities.txt", "r")
contents = infile.read()   # whole file as one string
infile.close()
print(contents)

Behind the scenes, the file keeps a read position — a marker for where the next read will begin. It starts at the front of the file; each readline moves it past the line just returned, so successive calls walk through the file one line at a time.

Stripping the newline

Because readline hands back the '\n' at the end of each line, you usually want to remove it before using the value. The string method rstrip strips characters from the right end of a string:

read_lines.py
infile = open("cities.txt", "r")

line1 = infile.readline()
line1 = line1.rstrip("\n")   # remove the trailing newline

print("First city:", line1)
infile.close()
A conversion gotcha

Writing and reading numeric data

A text file holds text, so numbers need converting on the way in and on the way out. This trips up beginners constantly, so it's worth a section of its own.

Going out: the write method only accepts strings, so convert each number with the str function before writing it.

write_scores.py
score = 95
outfile = open("scores.txt", "w")
outfile.write(str(score) + "\n")   # number -> string -> file
outfile.close()

Coming in: every value read from a text file arrives as a string, even if it looks like a number. Before doing arithmetic, convert it back with int or float.

read_scores.py
infile = open("scores.txt", "r")
line = infile.readline()
score = int(line)        # string -> number
print(score + 5)        # now arithmetic works: 100
infile.close()
The classic mistake

Forgetting the conversion gives you string behavior where you expected math. "95" + 5 raises an error, and "95" + "5" produces "955", not 100. When a number read from a file misbehaves, the missing int or float is almost always why.

Processing many items

Using loops to process files

Files usually hold more data than you'd handle by hand, and often you don't know how many items are in one ahead of time. That calls for a loop — and a way to detect the end of the file.

When readline reaches the end of a file, it returns an empty string (''). That empty string works as a sentinel: read a first line before the loop, then keep looping while the line isn't empty, reading the next line at the bottom of each pass.

while_readline.py
infile = open("cities.txt", "r")

line = infile.readline()      # priming read
while line != "":
    print(line.rstrip("\n"))
    line = infile.readline()  # read the next line

infile.close()

The simpler for loop

Python offers a much cleaner shortcut: a for loop can iterate directly over a file object, handing you one line per pass and stopping automatically at the end of the file. No priming read, no sentinel test.

for_lines.py
infile = open("cities.txt", "r")

for line in infile:
    print(line.rstrip("\n"))

infile.close()
Structured data

Processing records

Real data usually has structure. A record is a complete set of data describing one item, and a field is a single piece of data within that record. A player record, for instance, might have three fields: a name, a level, and a score.

To store a record in a sequential text file, write its fields one after another — a common approach is one field per line. To read the record back, read the same number of lines in the same order.

write_record.py
name = "Rey"
level = 7
score = 2480

outfile = open("players.txt", "w")
outfile.write(name + "\n")
outfile.write(str(level) + "\n")
outfile.write(str(score) + "\n")
outfile.close()
read_record.py
infile = open("players.txt", "r")

name = infile.readline().rstrip("\n")
level = int(infile.readline())
score = int(infile.readline())

print(name, "-- level", level, "-- score", score)
infile.close()

Once a program can write and read records, the same ideas extend to everything you'd want to do with a data file: add records, display them, search for a specific one, modify a record, or delete it.

When files go wrong

File errors and exception handling

File work is one of the most common sources of exceptions in real programs. A filename gets misspelled, a file is moved or deleted between runs, a value in the file isn't the number you expected. None of these can be prevented by careful coding alone — you only find out by trying.

Recap from Week 6

You already know the machinery: an exception is a runtime error that halts the program with a traceback unless it is handled, and a try/except statement handles it — the risky statements go in the try suite, and a matching except clause runs only if that type is raised. as err captures the exception object, else runs when nothing failed, and finally runs every time. If any of that is hazy, revisit Week 6 before continuing — this section applies it to files.

The exceptions file work raises

TypeRaised when…
FileNotFoundErrora file opened for reading with 'r' does not exist.
PermissionErrorthe file exists but the operating system won't allow the access requested.
ValueErrora value read from the file can't be converted — int("N/A").
OSErrora broader input/output failure; FileNotFoundError and PermissionError are both kinds of OSError.

Notice that only the first two are about the file itself. The third is the conversion problem from earlier in this module arriving as an exception — which is why a single try around file work often needs more than one except clause.

read_safely.py
try:
    infile = open("scores.txt", "r")
    score = int(infile.readline())
    print("Score:", score)
    infile.close()
except FileNotFoundError:
    print("That file isn't there.")
except ValueError:
    print("The first line wasn't a number.")
Why validation isn't enough

You could check whether a file exists before opening it — but the file could still be deleted in the instant between the check and the open. Handling the exception is the reliable approach: attempt the operation, and deal with the failure if it comes.

Closing the file no matter what

There is a bug hiding in the example above. If int() raises a ValueError, control jumps to the handler and infile.close() is never reached — the file stays open. This is exactly the job finally exists for:

always_close.py
infile = open("scores.txt", "r")
try:
    score = int(infile.readline())
    print("Score:", score)
except ValueError:
    print("The first line wasn't a number.")
finally:
    infile.close()      # runs whether or not the read failed

The open now sits outside the try, because if the file can't be opened there is nothing to close. Inside, finally guarantees the file is released along every path — success, handled failure, or an exception nobody catches.

The professional shortcut

Python offers a with statement that closes the file automatically, even when an exception occurs: with open("scores.txt", "r") as infile: followed by an indented block. You'll see it in real code constantly. This module uses the explicit open/close form so the steps stay visible, but it's worth recognizing.

Review

Check yourself

Predict each answer, then open the card. Even better, try it in the console above.

Q1What are the three steps for working with a file?▸

Open the file, process it (read or write), then close it.

Q2What's the difference between opening a file in 'w' mode and 'a' mode?▸

'w' erases the file's existing contents and starts fresh. 'a' keeps the contents and adds new data at the end. Both create the file if it doesn't exist.

Q3Why concatenate '\n' when writing, and how do you remove it after reading?▸

write adds no line breaks, so you add '\n' to keep items on separate lines. After reading, readline includes that '\n', so you strip it with rstrip('\n').

Q4How does readline signal that you've reached the end of the file?▸

It returns an empty string, ''. A while line != "": loop uses that as its stopping sentinel.

Q5Which exception does opening a missing file for reading raise, and why can't you prevent it by checking first?▸

FileNotFoundError. Checking that the file exists doesn't help, because it could be deleted in the instant between the check and the open. Attempt the operation and handle the failure.

Q6Why should infile.close() go in a finally suite rather than at the end of the try suite?▸

If a statement earlier in the try suite raises, control jumps to the handler and a close() at the end of the try suite is skipped — leaving the file open. finally runs on every path, so the file is always released.
