Classes & Object-Oriented Programming

So far your programs have been collections of functions that pass data around between them. Object-oriented programming flips that arrangement: instead of keeping data and the code that works on it apart, you bundle them together into objects. A class is the template that describes one kind of object; from it you stamp out as many instances as you need, each carrying its own data and its own set of methods.

A shift in thinking

Procedural vs. object-oriented programming

Everything you've written so far has been procedural: programs made of functions that perform tasks, with the data kept separate and passed from one function to the next. That works, but as programs grow, the data and the code that's supposed to protect it drift apart, and nothing stops a stray line somewhere from corrupting a value it shouldn't touch.

Object-oriented programming (OOP) takes a different stance. It bundles the data and the code that operates on that data together into a single unit called an object. Inside an object, the data items are called data attributes and the functions are called methods. Combining them this way has a name: encapsulation.

1Data hiding▸

An object's data attributes can be kept private — hidden from code outside the object, reachable only through its methods. This protects the data from accidental corruption, and it means outside code never has to know how the object stores things internally.

2Reusability▸

Because an object is a self-contained bundle, the same well-designed class can be reused in many different programs — the same FuelTank could serve a flight simulator, an inventory tracker, or a refueling-logistics tool.

Two words to keep straight

Classes and objects (instances)

A class is code that specifies the data attributes and methods that a particular kind of object will have. It is not itself an object — it's the description. An instance (also just called an object) is a concrete thing built from that class.

Think of an injection mold on a factory floor. The mold isn't a part — it's the specification for a part. Press it once and you get one part; press it again and you get another. Each part is its own physical object, yet all of them share the shape the mold defines. The mold is the class; each part is an instance. You can make as many instances of one class as you need.

Writing the template

Defining a class and the self parameter

A class definition is a set of statements that define the class's methods and data attributes. It begins with the keyword class, the class name, and a colon. By convention class names start with an uppercase letter and use CapWords.

first_class.py
class FuelTank:
    def report(self):
        print("I am a fuel tank.")

A method is defined just like any other function, with one rule: its first parameter is always self. The self parameter refers to the specific object the method is working on. You don't pass it yourself — Python supplies it automatically when you call the method through an instance.

To create an instance, call the class name like a function. To call a method on it, use dot notation:

use_it.py
tank = FuelTank()      # create an instance
tank.report()         # call a method on it — self is passed automatically
# I am a fuel tank.
Why self?

When you write tank.report(), Python turns it into "run report with self set to tank." That's how a method knows which object's data to use when many instances exist. Every method lists self first, even though you never pass it in the call.

Setting up an object

The __init__ initializer

An empty tank isn't very useful. The initializer method, named __init__ (two underscores on each side), runs automatically the moment an instance is created. Its job is to set up the object's data attributes. It's usually the first method in a class, and it can take parameters beyond self — values needed to build the object.

fueltank.py
class FuelTank:
    def __init__(self, capacity):
        self.capacity = capacity   # a data attribute, set from the parameter
        self.level = 0            # every new tank starts empty

    def fill(self, amount):
        self.level = self.level + amount

    def drain(self, amount):
        self.level = self.level - amount

Assigning to self.capacity inside a method creates a data attribute that belongs to the object. Now create a tank and the initializer runs for you:

build_tank.py
tank = FuelTank(60)    # __init__ runs with capacity = 60, level = 0
tank.fill(25)
print(tank.level)     # 25
print(tank.capacity)  # 60
The double underscores

__init__ is one of several specially named methods Python recognizes by its __name__ pattern. You never call it directly — writing FuelTank(60) is what triggers it.

Many objects, many states

Instance attributes and independent state

An instance attribute belongs to one specific object. Because each instance gets its own set of attributes, you can create many tanks and change them independently — filling one has no effect on the others.

three_tanks.py
tank_a = FuelTank(60)
tank_b = FuelTank(60)
tank_c = FuelTank(60)

tank_a.fill(40)
tank_c.fill(55)        # tank_b is left untouched

print(tank_a.level, tank_b.level, tank_c.level)
# 40 0 55
Protecting the data

Hiding attributes, accessors, and mutators

Our first FuelTank exposed level and capacity directly — any code anywhere could set tank.level = 9999 and overfill it. Good OOP keeps an object's data attributes private, reachable only through the object's own methods. In Python you signal that by starting the attribute name with two underscores.

fueltank_private.py
class FuelTank:
    def __init__(self, capacity):
        self.__capacity = capacity    # private: note the two leading underscores
        self.__level = 0

    def fill(self, amount):            # MUTATOR: changes the data
        self.__level = self.__level + amount
        if self.__level > self.__capacity:
            self.__level = self.__capacity   # guard: never overfill

    def drain(self, amount):           # MUTATOR
        self.__level = self.__level - amount
        if self.__level < 0:
            self.__level = 0             # guard: never below empty

    def get_level(self):               # ACCESSOR: returns, doesn't change
        return self.__level

    def get_capacity(self):            # ACCESSOR
        return self.__capacity

Two kinds of methods give controlled access to private data:

AAccessor methods (getters)▸

Return the value of an attribute without changing it — a safe way for outside code to read the data. Here, get_level and get_capacity.

MMutator methods (setters)▸

Store or change an attribute's value, and they can enforce rules while doing it. Here, fill and drain refuse to push the level above capacity or below zero — protection the bare attribute could never offer.

This is the payoff of encapsulation

Because __level is private and can only move through fill and drain, the tank can guarantee its level stays between 0 and capacity. The rules live with the data they protect.

Storing classes in modules

A class is often saved in its own .py file (a module) so many programs can import it. The same FuelTank class could live in fueltank.py and be imported wherever it's needed — the reusability we mentioned at the start.

Describing an object

The __str__ method

An object's state is the set of its attribute values at a given moment. It's handy to turn that state into readable text. Define a method named __str__ that returns a string, and Python will call it automatically whenever the object is passed to print or to the str function.

add_str.py
    def __str__(self):
        return f"FuelTank: {self.__level} of {self.__capacity} units"

With that method in place, printing the object just works — no need to dig out each attribute by hand:

show_state.py
tank = FuelTank(60)
tank.fill(25)
print(tank)      # FuelTank: 25 of 60 units   ← __str__ ran automatically
Objects on the move

Passing objects as arguments

Methods and functions often need to accept objects. When you pass an object as an argument, you pass a reference to it — not a copy. The receiving function therefore works on the actual object: it can call the object's methods and, through mutators, change its data.

pass_object.py
def top_off(tank):
    # works through the object's own methods
    needed = tank.get_capacity() - tank.get_level()
    tank.fill(needed)

my_tank = FuelTank(60)
my_tank.fill(20)
top_off(my_tank)              # passes a reference to the real object
print(my_tank.get_level())     # 60  — the original tank was changed
Reference, not copy

Because top_off received a reference, the fill it performed affected the same tank the caller holds. This is powerful — and a reason mutators that enforce rules matter: any code holding a reference can change the object, so the object must keep itself valid.

From problem to design

Finding the classes in a problem

When you start an object-oriented program, the first job is to decide what the classes are. A reliable technique works straight from a written description of the problem:

  1. Get a written description of the problem domain.
  2. Identify every noun (and noun phrase) — each is a candidate class.
  3. Refine the list: drop nouns that mean the same thing, ones the program doesn't care about, ones that are really individual objects rather than classes, and ones that are just simple values.

Take this short description:

Problem domain

"A refueling crew tracks each fuel tank on an aircraft. A tank has a capacity and a current level. The crew fills a tank and drains it, and reads its level before a flight."

Pull the nouns and decide what each becomes:

Candidate nounDecision
fuel tankKeep — a real thing with data and behavior. This becomes the FuelTank class.
capacity, levelDrop as classes — these are simple values, so they become data attributes of FuelTank.
crew, aircraft, flightDrop for now — outside what this small program needs to model. (A larger system might promote them to classes.)

Identifying responsibilities

Once you have a class, ask what it is responsible for knowing and doing. What it knows becomes its data attributes; what it does becomes its methods.

FuelTank is responsible for…Becomes…
knowing its capacity and current levelattributes __capacity, __level
filling, draining, and reporting its levelmethods fill, drain, get_level
The whole arc, in one line

Nouns point to classes, the things a class knows point to data attributes, and the things it does point to methods. That's how the FuelTank on this page was designed before a single line was typed.

Review

Check yourself

Predict each answer, then open the card. Even better, try it in the console above.

Q1What's the difference between a class and an instance?▸

A class is the description — the code specifying what data attributes and methods a kind of object has. An instance (object) is a concrete thing built from that class. One class can produce many instances, each with its own data.

Q2Every method lists self as its first parameter. What is self, and do you pass it when calling?▸

self refers to the specific object the method is working on. You don't pass it — writing tank.fill(10) makes Python set self to tank automatically. It's how a method knows which instance's data to use.

Q3When does __init__ run, and what is it for?▸

It runs automatically the moment an instance is created — FuelTank(60) triggers it. Its job is to set up the object's data attributes, often from parameters passed in.

Q4Why start a data attribute's name with two underscores, as in __level?▸

The __ prefix makes the attribute private, so code outside the class can't reach it through the normal name. That forces all access through the object's methods, which can enforce rules and prevent accidental corruption.

Q5What's the difference between an accessor and a mutator method?▸

An accessor (getter) returns an attribute's value without changing it — e.g. get_level. A mutator (setter) stores or changes an attribute, and can enforce rules while doing so — e.g. fill, which refuses to exceed capacity.

Q6How do you get print(tank) to show a readable description of an object?▸

Define a __str__ method that returns a string built from the object's attributes. Python calls it automatically when the object is passed to print or str.

Q7If you pass an object to a function and the function calls a mutator on it, is the caller's object affected?▸

Yes. Passing an object passes a reference, not a copy, so the function works on the same object the caller holds. A mutator called inside the function changes that real object.

Q8In a UML class diagram, what goes in each of the three compartments, and what do + and − mean?▸

Top: the class name. Middle: the data attributes. Bottom: the methods. A leading + marks a public member and a leading − marks a private one — in Python, private corresponds to the __ name prefix.

Designing programs around objects that bundle data with the code that acts on it.
object
An entity that contains data attributes and methods.
data attribute
A data item stored inside an object.
method
A function defined inside a class that operates on an object's data.
encapsulation
Combining data and the code that works on it into a single object.
data hiding
Keeping an object's data attributes private, reachable only through its methods.
object reusability
The ability to use the same well-designed class in many programs.
class
Code that specifies the data attributes and methods of a kind of object.
instance
A specific object created from a class; one class can have many.
class definition
The statements, beginning with class Name:, that define a class.

An attribute named with a leading __ so outside code can't reach it directly.
accessor method

mutator method
