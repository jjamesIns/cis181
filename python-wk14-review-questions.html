True or False

10 × 1 pt = 10
  1. T / F

    A subclass is a more specialized version of its superclass.

  2. T / F

    A superclass inherits the methods its subclasses define.

  3. T / F

    A subclass can add methods that the superclass does not have.

  4. T / F

    Omitting super().__init__() from a subclass initializer has no effect.

  5. T / F

    An overriding method must have the same name as the method it overrides.

  6. T / F

    An overriding method may call the superclass version and add to its result.

  7. T / F

    The version of an overridden method that runs is decided by the object's actual class.

  8. T / F

    isinstance returns True only when the object's class matches exactly.

  9. T / F

    Exception classes can form an inheritance hierarchy just like any other classes.

  10. T / F

    A method that raises an exception should change the object's data first, then validate.

Short Answer · 2 points each

  1. The "is a" relationship.A relationship in which one thing is a specialized version of another — a fuel tank is a tank, a manager is an employee. The general class is the superclass and the specialized one is the subclass. Accept any sound example where the subclass genuinely is a kind of the superclass.
  2. Superclass and subclass.The superclass (also called the base class) is the general class. The subclass (also called the derived class) is the specialized one. The subclass receives all of the superclass's attributes and methods, and may add new ones of its own.
  3. Subclass syntax.class FuelTank(Tank): — the superclass name goes in parentheses after the subclass name. The parentheses declare the "is a" relationship: everything defined in Tank is now part of FuelTank as well.
  4. super().__init__().It runs the superclass's initializer so the inherited attributes are created. Without it, those attributes never exist — and the first inherited method that tries to use one raises an AttributeError, even though the method itself is perfectly correct.
  5. Reducing duplication.Behavior common to every subclass is written once in the superclass. If Tank defines fill, get_level, and get_capacity, then FuelTank and PressurizedTank both get all three without a line of code — and a fix to fill improves both at once. Each subclass writes only what makes it different.
  6. UML inheritance.A line with an open (hollow) triangular arrowhead pointing from the subclass to the superclass — toward the more general class. The subclass box lists only the members it adds, because the arrow already declares that everything in the superclass is present.
  7. Polymorphism.An object's ability to take different forms, so the same method call does the right thing for whatever object it lands on. It needs two things: a superclass method that a subclass overrides, and Python selecting the version based on the object's actual type at the moment of the call.
  8. Overriding.Defining a method in a subclass with the same name as one in the superclass, so the subclass version runs for subclass objects. The override may extend the superclass version — calling it with super() and adding to the result — or replace it entirely and ignore it.
  9. isinstance.It returns True if the object is an instance of the given class or of any subclass of it, and False otherwise. A function uses it to confirm it received a usable object before calling a method — without the check, the wrong type raises an AttributeError.
  10. Exception hierarchies.Because an exception class is a class like any other, specific errors can be subclasses of a common base. That lets a caller choose its level of detail: except TankError catches every tank problem in one handler, while except OverfillError responds to just that one. Unrelated classes would force the caller to list every type separately.
  11. Detection vs. handling.The method detects the invalid value and raises; the caller handles it and decides what to do. Separating them is useful because the class knows what counts as invalid but cannot know the right response — a script might print a message, a GUI might show a dialog, a batch job might log and continue. One class serves all of them.

  1. Step 3 — reusing the superclass text.super().__str__(). It runs Employee's version, returning the formatted name and salary, and the override appends the report count to it. The currency formatting exists in exactly one place, so a change to it updates both classes.
  2. Step 4 — why the lines differ.Each object ran its own __str__. Python chose the version by the object's actual class — Employee's for Ana, Manager's override for Dev — even though the loop makes one identical call. The term is polymorphism.
  3. Step 5 — inherited give_raise.Manager inherits every method Employee defines, and give_raise was never overridden — so the superclass version runs unchanged. This is the reuse inheritance exists for: the raise logic and its validation are written once and serve both classes.
  4. Step 7 — why a Manager counts as an Employee.isinstance returns True for the class or any subclass of it, and Manager is a subclass of Employee. That reflects the "is a" relationship itself: a manager is an employee, so any code written to work with employees works with managers too.

Exercise 2 · A Robust Tank Hierarchy — 14 points

interactive mode
>>> class TankError(Exception): pass
>>> class NegativeAmountError(TankError): pass
>>> class OverfillError(TankError): pass
>>> class Tank:
...     def __init__(self, capacity):
...         self.__capacity = capacity
...         self.__level = 0
...     def fill(self, amount):
...         if amount < 0:
...             raise NegativeAmountError(f"cannot be negative: {amount}")
...         if self.__level + amount > self.__capacity:
...             raise OverfillError(f"{amount} would overflow")
...         self.__level = self.__level + amount
...     def get_level(self):
...         return self.__level
...     def get_capacity(self):
...         return self.__capacity
...     def __str__(self):
...         return f"{self.__level} of {self.__capacity} units"
...
>>> t = Tank(60); t.fill(20); print(t)
20 of 60 units
>>> for amount in [-5, 500]:
...     try:
...         t.fill(amount)
...     except TankError as err:
...         print(type(err).__name__, "-", err)
...
NegativeAmountError - cannot be negative: -5
OverfillError - 500 would overflow
>>> print(t)
20 of 60 units
>>> class FuelTank(Tank):
...     def __init__(self, capacity, grade):
...         super().__init__(capacity)
...         self.__grade = grade
...     def get_grade(self):
...         return self.__grade
...     def __str__(self):
...         return super().__str__() + f", {self.__grade} fuel"
...
>>> f = FuelTank(60, "Jet A"); f.fill(25)
>>> for item in [t, f]:
...     print(item)
...
20 of 60 units
25 of 60 units, Jet A fuel
>>> f.fill(500)
OverfillError: 500 would overflow
  1. Step 2 — why subclass TankError.It gives the caller a choice of precision. One except TankError clause catches every tank problem, because both specific errors are TankErrors — while a caller that needs to treat an overfill differently can still write except OverfillError. If both inherited from Exception directly, there would be no single name covering "any tank problem," and every caller would have to list them all.
  2. Step 3 — why validate first.Because raise ends the method immediately, any statement after it is skipped. Putting both checks before the line that changes __level guarantees an invalid call leaves the object exactly as it was. Validating after the change would corrupt the tank and then complain about it — the damage would already be done.
  3. Step 4 — one handler, two types.Both exceptions are subclasses of TankError, and an except clause catches the named class and any subclass of it. This is the same subclass rule isinstance follows — the "is a" relationship applied to exception handling.
  4. Step 5 — the level is unchanged.Still 20 of 60 units after two failed attempts. Both raises happened before the assignment, so the invalid amounts never touched the data. This is what "the object protects its own validity" means in practice: a rejected operation leaves no trace.
  5. Step 7 — what the subclass got for free.FuelTank inherited fill whole — including both validity checks and both custom exceptions — so it enforces the same rules without a single line of its own. The subclass wrote only what makes it different: the grade and an extended __str__.

Common error to watch for. In FuelTank.__str__, writing self.__level instead of calling super().__str__() raises AttributeError: 'FuelTank' object has no attribute '_FuelTank__level'. Private attributes are name-mangled with the class that defined them, so a subclass cannot reach the superclass's private data directly — it must go through inherited methods. This is a genuinely useful lesson about what "private" means.
