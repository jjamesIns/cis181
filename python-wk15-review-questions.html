True or False

10 × 1 pt = 10
  1. T / F

    Every recursive function must have at least one base case.

  2. T / F

    A recursive function may have more than one base case.

  3. T / F

    Some problems can be solved with recursion but not with a loop.

  4. T / F

    Each recursive call creates a fresh execution of the function with its own parameter values.

  5. T / F

    Recursion is usually faster than an equivalent loop.

  6. T / F

    A recursive function that never reaches its base case will run forever without any error.

  7. T / F

    In indirect recursion, no function ever calls itself directly.

  8. T / F

    The factorial of 0 is defined as 1.

  9. T / F

    The recursive Fibonacci function computes each value exactly once.

  10. T / F

    Recursion is a good fit for problems whose definition refers to a smaller version of themselves.

Exercise 1

Recursive String Tools

Strings are sequences, so they shrink the same way lists do. Build three recursive functions and watch the base case do the real work.

  1. Write a recursive function reverse(s) that returns the string reversed. Test it on "recursion", "abc", and the empty string. Explain: state your base case and why the empty string is the right place to stop.
  2. Write a recursive count_char(s, c) that returns how many times character c appears in s. Test it with count_char("banana", "a"). Explain: your recursive case has to decide whether to add 1 or 0 before recursing. Describe how you handled that.
  3. Write a recursive is_palindrome(s) that returns True when a string reads the same forward and backward. Compare the first and last characters, then recurse on what remains between them.
  4. Test it on "level", "racecar", "python", "a", and the empty string, recording each result. Explain: this function needs two stopping conditions. Name both and say what each one means.
  5. Now deliberately break it: remove the base case and call is_palindrome("level"). Record the exception exactly. Explain: name the exception and say in one sentence what it tells you about how Python runs recursive calls.
  6. Restore the base case. Then write a loop version of reverse and confirm it gives the same answer for "recursion".
  7. Explain: compare your two reverse functions. Which reads more clearly to you, and which would you expect to run faster on a very long string? Justify the speed answer using something from this module.

Exercise 2

Counting the Cost of Recursion

Build the classic recursive functions, then instrument one to prove why "correct" and "efficient" are different claims.

  1. Write the recursive factorial(n). Display factorial(0) through factorial(6) on one line using a comprehension.
  2. Write the recursive gcd(a, b) using Euclid's algorithm. Test it on (48, 18), (60, 24), and (17, 5). Then try gcd(24, 60) — the smaller number first. Explain: it still gives the right answer. Trace the first call and explain why the order fixes itself.
  3. Try gcd(10, 0) and record the exception. Explain: name it and say which line of the function caused it.
  4. Write the recursive fibonacci(n) with both base cases. Display the first eleven values using a comprehension.
  5. Now count the work. Add a global counter that increments on every entry to the function, and record the number of calls for fibonacci(5), fibonacci(10), and fibonacci(20), resetting the counter before each. Explain: the input grew by 15 and the call count exploded. What is the function doing repeatedly that causes this?
  6. Write a loop version of fibonacci that keeps the two previous values in variables, and confirm it produces the same eleven numbers. Explain: roughly how many steps does the loop version take for fibonacci(20)? Compare that with your counted number.
  7. Write the Towers of Hanoi move_disks function and run it for 3 disks, displaying every move. Then run it for 1, 2, and 4 disks and count the moves each time. Explain: give the move counts and describe the pattern. Is Hanoi a case where recursion is worth it? Defend your answer.

Short Answer · 2 points each

  1. Recursive functions.A function that calls itself. It needs more than the recursive call because a call with no way to stop would repeat forever — so it must also contain a decision, normally an if, that determines on each call whether to recurse again or stop and return a value.
  2. The two parts.The base case handles a problem small enough to solve directly, with no further recursion, and returns the answer. The recursive case reduces the problem to a smaller problem of the same structure, calls the function on it, and uses the returned result to build this call's answer.
  3. Depth of recursion.The number of times the function calls itself for a given starting call. It is determined by how far the starting argument is from the base case and how much each call reduces it — count_down(3) has a depth of 3.
  4. No reachable base case.The function keeps calling itself, each call consuming memory for its own execution, until Python stops it with a RecursionError — the message reads "maximum recursion depth exceeded." It does not run forever; Python enforces a limit.
  5. Smaller version of itself.Each recursive call must receive an argument closer to the base case. With a number, subtract from it — factorial(n) calls factorial(n - 1). With a list, remove an element — sum_all(numbers) calls sum_all(numbers[1:]), a list one shorter. Without this shrinking, the base case is never reached.
  6. Winding and unwinding.The calls wind down: factorial(4) calls factorial(3), which calls factorial(2), and so on to factorial(0) — each waiting, unable to finish until the call below returns. The base case returns 1, and the results unwind back up as each waiting call multiplies by its own n: 1, then 2, then 6, then 24.
  7. Direct vs. indirect.Direct recursion is a function calling itself — factorial calls factorial. Indirect recursion is a cycle through other functions — is_even calls is_odd, which calls is_even again; neither calls itself, yet the pair recurs.
  8. Fibonacci's inefficiency.Its recursive case makes two calls, and the two branches overlap — computing fibonacci(5) requires fibonacci(3) twice, fibonacci(2) three times, and so on. Nothing is remembered between calls, so the same values are recomputed from scratch and the call count grows explosively with n.
  9. Euclid's algorithm.Base case: when a % b == 0, return b. Recursive case: return gcd(b, a % b). It always terminates because each call replaces the pair with a strictly smaller remainder, so the second argument marches down toward 0 and the base case is reached.
  10. Towers of Hanoi.To move count disks from the source peg to the target: if there is only one disk, move it directly — that is the base case. Otherwise move the top count - 1 disks to the spare peg, move the single largest disk to the target, then move those count - 1 disks from the spare peg onto the target.
  11. Choosing between them.Any two of: whether the problem's own definition refers to a smaller version of itself (favors recursion); whether efficiency matters, since recursion carries call overhead (favors a loop); whether recursion makes the code dramatically clearer or merely different; and how deep the recursion would go, since very deep recursion risks a RecursionError.

Algorithm Workbench · 1 point each

  1. Trace 1.3 / 2 / 1 / Liftoff! — each on its own line. The print comes before the recursive call, so values appear on the way down.
  2. Trace 2.1 / 2 / 3 — counting up. The print comes after the recursive call, so nothing is displayed until the deepest call returns; the values then print as the recursion unwinds. Moving one statement reverses the output.
  3. Factorial's two cases.Base case: n == 0 returns 1. Recursive case: returns n * factorial(n - 1).
  4. Factorial values.a. 1 · b. 1 · c. 120 · d. 720
  5. Bug 1.There is no base case, so the function recurses forever and raises RecursionError. Fix by adding if n == 0: return 0 before the recursive line.
  6. Bug 2.The recursive call uses n + 1, moving away from the base case — n grows without limit and never equals 0, so it still raises RecursionError. A base case only helps if every call moves toward it. Change to total_to(n - 1).
  7. Correct total_to.def total_to(n): with if n == 0: return 0 then else: return n + total_to(n - 1).
  8. count_down_by.def count_down_by(n, step): with if n > 0: containing print(n) and count_down_by(n - step, step). The step must be passed along on every call.
  9. sum_all values.a. 0 · b. 7 · c. 22
  10. count_items.def count_items(items): with if len(items) == 0: return 0 then else: return 1 + count_items(items[1:]).
  11. Fibonacci values.0, 1, 1, 2, 3, 5, 8, 13
  12. gcd values.a. 6 · b. 12 · c. 1 · d. 12
  13. Tracing gcd(48, 18).gcd(48, 18) → 48 % 18 is 12, not 0 → gcd(18, 12) → 18 % 12 is 6 → gcd(12, 6) → 12 % 6 is 0, base case → returns 6. Three calls in total.
  14. reverse.Base case: an empty string returns the empty string. def reverse(s): with if len(s) == 0: return "" then else: return reverse(s[1:]) + s[0].
  15. Hanoi move counts.1 disk → 1 move; 2 → 3; 3 → 7; 4 → 15. Each added disk slightly more than doubles the total: the count is 2n − 1, because solving n disks means solving n − 1 twice plus one more move.
  16. Factorial as a loop.result = 1, then for i in range(1, n + 1): result = result * i, then return result. The recursive version mirrors the mathematical definition almost exactly, making it easy to verify as correct; the loop version is more efficient, since it avoids the overhead of a function call per step and cannot hit a recursion limit.

  1. Step 1 — the base case.An empty string returns an empty string. It is the right stopping point because every call removes one character with s[1:], so any string — of any length — eventually becomes empty. A reversed empty string is trivially itself, so no work is needed there. Accept a base case of len(s) <= 1 returning s.
  2. Step 2 — adding 1 or 0.Two acceptable approaches. Use an elif that returns 1 + count_char(s[1:], c) when the first character matches and plain count_char(s[1:], c) when it does not; or compute the 1-or-0 inline and always recurse. Either way the recursive call is identical in both branches — only the amount added differs.
  3. Step 4 — two stopping conditions.First, len(s) <= 1 returns True — a string of one character, or none, is trivially a palindrome, and this is what the recursion eventually shrinks to. Second, s[0] != s[-1] returns False — a mismatch settles the answer immediately and there is no reason to keep going. The first is the base case reached by success; the second is an early exit on failure.
  4. Step 5 — the exception.RecursionError: maximum recursion depth exceeded. It tells you Python keeps a record of every call that has not yet returned, and that this record has a limit — recursion is not free, and a function with no reachable base case exhausts that space rather than running forever.
  5. Step 7 — comparing the two.Clarity is a defensible judgment either way; credit any reasoned answer. The speed answer is not optional: the loop version should be faster, because the recursive version pays function-call overhead for every character and also builds a new sliced string on each call. Full credit requires naming call overhead or the repeated slicing.

  1. Step 2 — why gcd(24, 60) still works.On the first call 24 % 60 is 24 — a remainder equal to the smaller number, and not 0 — so the function recurses as gcd(60, 24), which is the arguments in the order you expected. One wasted call puts them right, and the answer is 12. The algorithm is self-correcting, so no size check is needed.
  2. Step 3 — gcd(10, 0).ZeroDivisionError: integer modulo by zero, raised by the base-case test a % b == 0 — the % operator cannot take 0 as its right operand. A robust version would guard against b == 0 before testing, or return a in that case.
  3. Step 5 — why the calls explode.The recursive case makes two calls, and their subtrees overlap heavily — fibonacci(20) recomputes fibonacci(18), fibonacci(17), and everything below them enormous numbers of times, because nothing is remembered between calls. The call count grows roughly exponentially: 15 calls at n=5, 177 at 10, and 21,891 at 20.
  4. Step 6 — the loop's cost.The loop version takes about 20 steps for fibonacci(20) — one per value — against 21,891 recursive calls for the identical answer. It is faster because it keeps the two previous values in variables and never recomputes anything. Same result, same eleven numbers, vastly different work.
  5. Step 7 — Hanoi.Move counts: 1, 3, 7, 15 for 1 through 4 disks — the pattern is 2n − 1, each disk slightly more than doubling the total. Hanoi is a case where recursion is worth it: the recursive solution is four lines and reads like the strategy itself, while an iterative solution is far harder to write and to verify. The move count is dictated by the puzzle, not by the recursion — unlike Fibonacci, recursion here costs nothing extra in work. Accept a well-argued opposing view that notes the exponential growth, provided the student distinguishes the puzzle's inherent cost from recursion's overhead.

If a student reports 7 instead of 15 for fibonacci(5), that is the cause — a good opportunity to point out that base-case calls are real calls too.
