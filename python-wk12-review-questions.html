Short Answer · 2 points each

  1. Procedural vs. object-oriented.Procedural programs are built from functions that perform tasks, with the data kept separate and passed between them. Object-oriented programs bundle the data and the code that operates on it into a single unit. The problem OOP addresses: as a program grows, data and the code meant to protect it drift apart, and nothing prevents a stray statement from corrupting a value it should not touch.
  2. Encapsulation.Combining data and the code that operates on that data into one unit — an object. Inside the object, the data items are called data attributes and the functions are called methods.
  3. Two benefits.Data hiding — attributes can be kept private, protecting them from accidental corruption and freeing outside code from needing to know how the object stores things internally. Reusability — because an object is self-contained, one well-designed class can serve many different programs.
  4. Class vs. instance.A class is code specifying the attributes and methods a kind of object will have — a description, not an object itself. An instance is a concrete object built from that class, and one class can produce as many as needed. Accept any sound analogy: a blueprint and the houses built from it, a cookie cutter and the cookies, a mold and the parts pressed from it.
  5. The self parameter.self refers to the specific object the method is working on. Every method lists it first so that, when many instances exist, the method knows whose data to use. Python supplies its value automatically — writing tank.report() becomes "run report with self set to tank."
  6. __init__.The initializer method. Its job is to set up the object's data attributes, and it can accept parameters beyond self for values needed to build the object. It runs automatically the moment an instance is created — writing FuelTank(60) is what triggers it. You never call it by name.
  7. Instance attributes.An attribute belonging to one specific object, created by assigning to self.name inside a method. Because every instance receives its own set, three objects built from the same class each carry their own values — changing one leaves the others untouched.
  8. Making an attribute private.Start its name with two underscores, as in self.__level. The reason is data hiding: outside code cannot reach the attribute directly, so it cannot corrupt it, and all access is forced through the object's own methods where rules can be enforced.
  9. Accessor vs. mutator.An accessor (getter) returns an attribute's value without changing it — a safe way for outside code to read. A mutator (setter) stores or changes a value, and can enforce rules while doing so. Example: a fill mutator that caps the level at capacity, or a withdraw that refuses an amount exceeding the balance — protection a bare public attribute could never offer.
  10. __str__.It returns a string describing the object's state. Unlike an ordinary method, you never call it by name — Python invokes it automatically whenever the object is passed to print or to str.
  11. Finding classes.Start from a written description of the problem domain, identify every noun and noun phrase as a candidate class, then refine the list by dropping duplicates, nouns the program does not care about, ones that are really individual objects rather than classes, and ones that are just simple values. The nouns become classes; what a class is responsible for knowing becomes its data attributes, and what it is responsible for doing becomes its methods.

Algorithm Workbench · 1 point each

  1. Class header.class Thermostat:
  2. A method.def report(self): then indented print('Thermostat online'). No credit without self.
  3. Instance and call.unit = Thermostat() then unit.report()
  4. __init__.def __init__(self, target): with self.__target = target and self.__current = 0.
  5. Accessor.def get_target(self): return self.__target
  6. Mutator with a guard.def set_target(self, value): containing if value >= 10 and value <= 30: self.__target = value. Accept an if value < 10 or value > 30: return guard clause.
  7. __str__.def __str__(self): return f"Target {self.__target}, current {self.__current}"
  8. Trace 1.2 0 — a and b are separate instances, each with its own count. Bumping a twice leaves b at 0.
  9. Trace 2.1 — b = a does not create a second object; both names reference the same instance, so bumping through b is visible through a. Compare with Trace 1: the difference is one assignment.
  10. Bug 1.TypeError: Greeter.hello() takes 0 positional arguments but 1 was given. The method omits self, but Python passes the instance automatically — so one argument arrives at a method that accepts none. Add self to the header.
  11. Bug 2.AttributeError: 'Tank' object has no attribute '__capacity'. The two leading underscores make the attribute private, so it cannot be reached from outside the class. Add an accessor such as get_capacity and call that instead.
  12. warm_up.def warm_up(unit): unit.set_target(unit.get_target() + 2) — accessor to read, mutator to write; no direct attribute access.
  13. Why it can change the caller's object.Passing an object passes a reference to it, not a copy. The parameter and the caller's variable therefore refer to the same object, so a mutator called inside the function changes the object the caller still holds.

Exercise 1 · The Bank Account Class — 14 points

interactive mode
>>> class BankAccount:
...     def __init__(self, owner, balance):
...         self.__owner = owner
...         self.__balance = balance
...     def get_owner(self):
...         return self.__owner
...     def get_balance(self):
...         return self.__balance
...     def deposit(self, amount):
...         if amount <= 0:
...             raise ValueError("deposit must be positive")
...         self.__balance += amount
...     def withdraw(self, amount):
...         if amount > self.__balance:
...             raise ValueError("insufficient funds")
...         self.__balance -= amount
...     def __str__(self):
...         return f"{self.__owner}: ${self.__balance:,.2f}"
...
>>> account = BankAccount("Rey", 250.00)
>>> print(account)
Rey: $250.00
>>> account.deposit(125.50); print(account)
Rey: $375.50
>>> account.withdraw(80); account.get_balance()
295.5
>>> account.withdraw(10000)
ValueError: insufficient funds
>>> account.deposit(-5)
ValueError: deposit must be positive
>>> account.__balance
AttributeError: 'BankAccount' object has no attribute '__balance'
>>> second = BankAccount("Finn", 0)
>>> print(account); print(second)
Rey: $375.50
Finn: $0.00
  1. Step 3 — what made __str__ run.Passing the object to print. Python recognizes the specially named __str__ method and calls it automatically whenever an object is handed to print or str — which is why the account displays as readable text instead of something like <__main__.BankAccount object at 0x7f...>.
  2. Step 6 — the direct access attempt.AttributeError: 'BankAccount' object has no attribute '__balance'. The two leading underscores made the attribute private, so outside code cannot reach it. That is data hiding in action: the balance can now be changed only through deposit and withdraw, which is exactly what lets those methods enforce their rules. Without privacy, any statement anywhere could set the balance to any value and bypass every guard.
  3. Step 7 — the term.Instance attributes. Each object created from the class receives its own set, so account and second hold independent owners and balances even though one class defined them both.

Exercise 2 · The Library Book Class — 14 points

interactive mode
>>> class Book:
...     def __init__(self, title, author, copies):
...         self.__title = title
...         self.__author = author
...         self.__copies = copies
...     def check_out(self):
...         if self.__copies == 0:
...             return False
...         self.__copies -= 1
...         return True
...     def return_copy(self):
...         self.__copies += 1
...     def get_title(self):
...         return self.__title
...     def get_copies(self):
...         return self.__copies
...     def __str__(self):
...         return f"{self.__title} by {self.__author} ({self.__copies} available)"
...
>>> books = [Book("Dune", "Herbert", 2), Book("Emma", "Austen", 1)]
>>> for b in books:
...     print(b)
...
Dune by Herbert (2 available)
Emma by Austen (1 available)
>>> books[0].check_out(), books[0].get_copies()
(True, 1)
>>> books[1].check_out()
True
>>> books[1].check_out()
False
>>> books[1].return_copy(); print(books[1])
Emma by Austen (1 available)
>>> def restock(book, quantity):
...     for i in range(quantity):
...         book.return_copy()
...
>>> restock(books[1], 3); print(books[1])
Emma by Austen (4 available)
>>> sum(b.get_copies() for b in books)
5
  1. Step 4 — why return a value.Returning False tells the caller the checkout could not happen, so the calling code can respond — display "none available", offer a hold, try another title. Letting the count fall to -1 would leave the object in a state that is impossible in the real world, and the error would surface much later, far from its cause. The object protects its own validity, which is the point of a mutator. Accept also: raising an exception is a defensible alternative, since the caller must handle it either way.
  2. Step 6 — why the function changed the book in the list.Passing an object passes a reference to it, not a copy. The parameter book and the element in the list refer to the same object, so return_copy called inside the function operates on that one object. This is the same behavior as the list aliasing from Week 08 — one object, two names.
  3. Step 7 — why call an accessor.The accessor is a stable interface. If the class later stores its count differently — renaming the attribute, tracking total and loaned copies separately, computing availability — every caller that used get_copies() keeps working, because only the method body changes. Code that reached into the attribute directly would break everywhere at once. Accept also: the attribute is private, so direct access raises AttributeError.
PointsEarned for
4Class defined with three private attributes, both mutators, both accessors, and a correct __str__.
2Steps 3 and 5: two books in a list displayed by a loop; return handled correctly.
2Step 4: check_out returns True, True, then False without going negative.
2Step 4 explanation — returning a value keeps the object valid and lets the caller respond.
2Step 6: restock works, and reference semantics correctly explained.
2Step 7: total of 5 computed via accessors, with a sound reason for using them.
Common error to watch for. Writing self.__copies in one method and self.copies in another. Python creates the second one as a brand-new public attribute rather than reporting a mistake, so the object silently ends up with two separate counts. Worth demonstrating once — it is the hardest class bug for beginners to find.
