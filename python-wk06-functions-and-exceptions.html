Week 06

Exceptions
& Functions

Programs fail while they are running: a user types letters where a number belongs, a list turns out to be empty, a divisor lands on zero. Python signals these with exceptions. This module covers what exceptions are and how to catch them — and then puts them together with what you already know about functions. A function is a small promise: give it the right inputs and it returns a sensible result. When the inputs make that promise impossible to keep, the professional move is to raise — to stop and announce the problem — and let the calling code decide what to do.

Foundation

What an exception is

An exception is an error that occurs while a program is running. It is not a typo the interpreter catches before starting — the program was syntactically fine, it began executing, and then hit a situation it could not carry out. Left alone, an exception halts the program abruptly.

You have already met several without naming them. Each of the following is a perfectly legal Python statement that fails only when it actually runs:

runtime_failures.py
int('hello')      # ValueError — the text isn't a number
10 / 0              # ZeroDivisionError
[1, 2, 3][99]      # IndexError — no such position
'5' + 5             # TypeError — can't add a str and an int
Exception vs. syntax error

A syntax error breaks the language's grammar, so the interpreter refuses to run the program at all — nothing executes. An exception happens during execution: earlier statements already ran and produced their output before the failure. If you see output and then an error, you are looking at an exception.

Reading a traceback

When an exception goes unhandled, Python prints a traceback — a report naming the type of exception, a description, and the chain of calls that led there. Tracebacks look intimidating, but they have a reliable shape. Here is a program whose functions call one another:

averages.py
def average(numbers):
    return sum(numbers) / len(numbers)

def report(numbers):
    print("Average:", average(numbers))

report([])          # an empty list — nothing to average
the traceback
Traceback (most recent call last):
  File "averages.py", line 7, in <module>
    report([])
  File "averages.py", line 5, in report
    print("Average:", average(numbers))
  File "averages.py", line 2, in average
    return sum(numbers) / len(numbers)
ZeroDivisionError: division by zero

Read it from the bottom up. The last line is the one that matters: the exception type before the colon and a description after it. Above that, the call chain is listed oldest first — line 7 called report, which called average on line 5, and the actual failure happened on line 2.

The failure and the cause are in different places

Notice that average is where the program broke, but the mistake was made on line 7, where an empty list was passed in. That gap is exactly why the rest of this module matters: the function that discovers the problem is rarely the code that caused it.

Common built-in exception types

Python names its exceptions after what went wrong. Recognizing the common ones tells you where to look:

TypeOccurs when…
ValueErrora value is the right type but unacceptable — int('hello').
TypeErroran operation is applied to the wrong type — '5' + 5.
ZeroDivisionErrora division or modulo by zero is attempted.
IndexErrora sequence index is out of range.
KeyErrora dictionary key does not exist.
NameErrora name is used that has not been assigned.
FileNotFoundErrora file being opened for reading does not exist.

Some exceptions you can prevent with careful coding — validating input with a decision structure heads off many of them. Others you genuinely cannot prevent by checking alone: whether a file still exists, or whether what the user typed is a number, can only be discovered by trying. That is the situation exception handling exists for.

Responding

Catching exceptions with try / except

An exception handler is code that responds to an exception and keeps the program running. You write one with a try/except statement: the try suite holds the statements that might fail, and the except clause runs only if a matching exception is raised.

try_except.py
try:
    age = int(input("Enter your age: "))
    print("Next year you'll be", age + 1)
except ValueError:
    print("That wasn't a whole number.")

If a statement in the try suite raises the named exception, control jumps immediately to the handler — the rest of the try suite is skipped — and then continues after the whole statement. If nothing is raised, the handler is skipped entirely. An exception of a different type is not caught here and would still halt the program.

Handling more than one kind of error

When a try suite could fail in several ways, write an except clause for each type. A clause naming no type catches everything, so it must always come last:

multiple_except.py
try:
    total = int(count_text)
    share = budget / total
except ValueError:
    print("That wasn't a number.")
except ZeroDivisionError:
    print("Can't divide among zero people.")
Order matters

Putting a bare except: before a specific clause is a syntax error — Python reports default 'except:' must be last. Beyond that, catching everything is a blunt instrument: it swallows typos and unrelated bugs along with the error you meant to handle. Prefer naming the types you actually expect.

The exception object, else, and finally

When an exception is raised, Python creates an exception object carrying a description of the problem. Capture it with as to read that message:

as_err.py
try:
    value = int("not a number")
except ValueError as err:
    print("Problem:", err)
# Problem: invalid literal for int() with base 10: 'not a number'

Two optional clauses may follow, aligned with try and except:

elseRuns only when nothing failed▸

The else suite executes only if the try suite raised no exception. It is the place for work that should happen on success but that you don't want inside the try — keeping the try suite narrow means you catch only the errors you intended to.

finallyRuns every single time▸

The finally suite executes whether or not an exception occurred, and whether or not it was handled. It is the natural home for cleanup — releasing a resource, closing a connection — that must happen no matter how the block ends.

full_shape.py
try:
    quantity = int(entry)
except ValueError:
    print("Not a number.")      # only if it failed
else:
    print("Accepted:", quantity)  # only if it worked
finally:
    print("Entry processed.")    # always

When nothing handles it

If no except clause matches the exception's type — or the exception was raised outside any try suite — it goes unhandled. The program halts and prints the traceback you saw in the previous section. Handling an exception is therefore a deliberate choice: silence is not the default, crashing is.

Foundation

Detection vs. handling

So far the exceptions you have caught came from built-in operations. Now turn the question around: when your own function is handed something it cannot work with, what should it do? Put exceptions together with functions and a powerful design principle appears — a function should detect problems, but it usually shouldn't decide what to do about them.

Those are two different jobs, and they often belong to two different places in your code:

insideThe function detects the problem▸

A function knows the rules of its own job. It's the right place to notice that an argument is out of range, the wrong type, or otherwise impossible to work with. When it sees that, it raises an exception instead of returning a meaningless result.

outsideThe caller decides what to do▸

The code that called the function has the context to respond — re-ask the user, try a default, log it, or give up gracefully. It does this by handling the exception with try/except. The same function can be reused in many programs, each handling failure in its own way.

Throwing on purpose

The raise statement

You make a function raise an exception with the raise statement. You name an exception type and, in parentheses, a message explaining what went wrong:

raise_format.py
raise ExceptionType("a message describing the problem")

The moment a raise runs, the function stops immediately — nothing after it executes — and the exception begins traveling back to whoever called the function. Here's a small function that checks its argument before doing its work:

to_kelvin.py
def to_kelvin(celsius):
    if celsius < -273.15:
        raise ValueError("temperature is below absolute zero")
    return celsius + 273.15

print(to_kelvin(20))      # 293.15
print(to_kelvin(-300))    # ValueError: temperature is below absolute zero
Raise vs. print-and-return

A beginner's instinct is to print a warning and return something like 0 or None. The trouble is that the caller may not notice, and that bad value flows downstream causing a confusing error far from the real cause. Raising stops the problem at its source and forces the caller to deal with it.

Design judgment

When should a function raise?

A function should raise when it is asked to do something it cannot meaningfully do — when keeping its promise is impossible. The guiding rule: raise for the exceptional, return for the normal.

Good reasons to raise

  • Invalid arguments. A value is out of range, empty when it must be non-empty, or the wrong type. The function's precondition is violated.
  • An impossible request. Withdrawing more money than an account holds; taking the average of an empty list; a quantity that can't be negative.
  • A broken assumption. Something the function relied on turned out not to be true, so continuing would produce nonsense.
withdraw.py
def withdraw(balance, amount):
    if amount <= 0:
        raise ValueError("amount must be positive")
    if amount > balance:
        raise ValueError("insufficient funds")
    return balance - amount

When not to raise

Not every unusual outcome is an error. If something is a normal, expected possibility that the caller will routinely check, a plain return value is often clearer than an exception.

A useful test

Ask: "Is this a result the caller might reasonably expect on a good day?" If yes — like a search that finds nothing — consider returning a value such as None or an empty list. If it means the function simply cannot do its job correctly, raise. Reserve exceptions for the genuinely exceptional.

Be specific

Choosing the exception type and message

Python defines many built-in exception types. Raise the most specific one that fits, so callers can catch exactly what they expect. A vague exception forces callers to either catch everything or guess.

Built-in typeRaise it when…
ValueErrorthe argument is the right type but an unacceptable value (out of range, empty, malformed).
TypeErrorthe argument is the wrong type entirely (a string where a number is required).
ZeroDivisionErrora division or modulo by zero would occur.
IndexErrora sequence index is out of range.
KeyErrora dictionary key doesn't exist.
RuntimeErrorsomething went wrong that no more specific type describes.

Write the message for the person who will read the traceback. State what was expected and, where useful, what was actually received:

good_messages.py
def set_quantity(n):
    if not isinstance(n, int):
        raise TypeError("quantity must be an int, got " + type(n).__name__)
    if n < 0:
        raise ValueError("quantity cannot be negative: " + str(n))
    return n
Avoid

A bare raise Exception("error") tells the caller almost nothing and can only be caught with a broad except Exception, which also swallows unrelated bugs. Specific type + specific message = code that's easy to handle and easy to debug.

Functions meet classes

Defining your own exception types

Sometimes none of the built-in types says exactly what went wrong in your program. You can define your own by writing a class that inherits from Python's Exception class. Even an empty class body is enough to create a usable, distinct exception type.

custom_exception.py
class TemperatureError(Exception):
    """Raised when a temperature is physically impossible."""
    pass

def to_kelvin(celsius):
    if celsius < -273.15:
        raise TemperatureError("below absolute zero: " + str(celsius))
    return celsius + 273.15

Why bother, instead of reusing ValueError?

  • Intent is obvious. The name TemperatureError documents precisely what category of failure this is.
  • Callers can catch it exactly. A program can write except TemperatureError to respond to this problem without accidentally catching every other ValueError in the call.
  • It can carry extra data. Because it's a class, you can give it attributes (the offending value, a suggested fix) for the handler to use.
Inherit from Exception

Always base custom exceptions on Exception (or a more specific built-in). That keeps them catchable by a general except Exception handler and marks them clearly as errors, distinct from ordinary objects.

The caller's job

Handling exceptions where the function is used

A function that raises is only half the story. The program that calls it wraps the call in a try/except statement: the risky call goes in the try suite, and a matching except clause runs only if that type of exception is raised.

handling.py
try:
    kelvin = to_kelvin(reading)
    print("Converted:", kelvin)
except TemperatureError as err:
    print("Could not convert:", err)   # err holds the message

A few moving parts make this flexible:

  • Specific clauses, in order. You can list several except clauses for different types. A catch-all except (no type) must come last.
  • as err captures the exception object so you can read its message.
  • else runs only if the try suite raised nothing; finally runs every time, for cleanup.

Exceptions travel up the call chain

If the function that raises doesn't handle the exception (it usually shouldn't), the exception propagates to its caller, and so on up the chain, until some try/except catches it. If nothing does, the program halts with a traceback.

Bringing it together

Putting it together: a robust program

Here's the payoff. A validating function raises on bad input; the program calls it inside a loop, catches the exception, and simply asks again. The user can't crash the program no matter what they type — that's what we mean by robust.

robust_input.py
def get_rating(text):
    value = int(text)            # may raise ValueError
    if value < 1 or value > 5:
        raise ValueError("rating must be from 1 to 5")
    return value

def main():
    rating = None
    while rating is None:
        try:
            rating = get_rating(input("Rate us 1-5: "))
        except ValueError as err:
            print("Try again (" + str(err) + ")")
    print("Thanks! You rated us", rating)

main()
The pattern, in one breath

Write functions that raise when they can't keep their promise. Call them inside a try, and let the caller decide how to recover. The detection lives in one place, the response lives where the context is — and the program keeps running.

Review

Check yourself

Predict each answer, then open the card. Even better, try it in the console above.

Q1What is the difference between a syntax error and an exception?▸

A syntax error breaks the language's grammar, so the interpreter refuses to run the program and nothing executes. An exception happens during execution — earlier statements already ran. Output followed by an error means you are looking at an exception.

Q2Which line of a traceback should you read first, and what does it tell you?▸

The last line. It names the exception type before the colon and describes the problem after it. The lines above show the chain of calls that led there, oldest first — useful for finding where the bad value originated.

Q3In a try/except, what happens to the rest of the try suite when an exception is raised partway through?▸

It is skipped entirely. Control jumps straight to the matching except clause, then resumes after the whole statement — the remaining statements in the try suite never run.

Q4When do the else and finally suites run?▸

else runs only when the try suite raised nothing. finally runs every time — exception or not, handled or not — which makes it the right place for cleanup.

Q5Why is it usually better for a function to raise an exception than to print a warning and return a default value?▸

A returned default can slip by unnoticed and cause a confusing failure later, far from the real cause. Raising stops the problem at its source and forces the caller to handle it deliberately.

Q6What two pieces does a raise statement typically include?▸

An exception type and a message: raise ValueError("..."). The type lets callers catch it specifically; the message explains what went wrong.

Q7Give the rule of thumb for deciding whether to raise or to return a value.▸

Raise for the exceptional, return for the normal. If an outcome is something the caller might reasonably expect on a good day (like a search finding nothing), return a value. If the function simply can't do its job, raise.

Q8Why prefer ValueError over a bare Exception when an argument is out of range?▸

A specific type lets the caller catch exactly that error without also swallowing unrelated bugs. except Exception is a blunt instrument that hides problems you didn't mean to catch.

Q9How do you define your own exception type, and why might you?▸

Write a class that inherits from Exception — even an empty body works. It makes intent obvious, lets callers catch exactly your error, and can carry extra data about what failed.

Q10If a function raises an exception but has no try/except, what happens?▸

The exception propagates up to whoever called the function, then to that caller, and so on, until some try/except handles it. If none does, the program halts with a traceback.

Q11In the robust input loop, what makes it impossible for bad input to crash the program?▸

The call to the validating function sits inside a try within a loop. Any ValueError it raises is caught, a message is shown, and the loop simply asks again — only a valid value ends the loop.
