A specialized version

Introduction to inheritance

In the real world many objects are specialized versions of more general ones. A fuel tank and a pressurized tank are both, before anything else, tanks: they hold a capacity, track a level, and can be filled and drained. Each then adds something of its own — a fuel grade, a pressure rating. That relationship has a name: the "is a" relationship. A fuel tank is a tank.

Inheritance lets you express an "is a" relationship between classes. You write the general class once — the superclass (or base class) — and then build a specialized subclass (or derived class) that inherits all of the superclass's attributes and methods, and can add new ones of its own.

Writing the relationship

Defining a subclass

Here is the general Tank — essentially the class you built in Week 12, holding the parts every tank shares:

tank.py
class Tank:
    def __init__(self, capacity):
        self.__capacity = capacity
        self.__level = 0

    def fill(self, amount):
        self.__level = self.__level + amount
        if self.__level > self.__capacity:
            self.__level = self.__capacity

    def get_level(self):
        return self.__level

    def get_capacity(self):
        return self.__capacity

To make a subclass, put the superclass name in parentheses after the subclass name: class FuelTank(Tank):. The subclass's initializer first calls the superclass initializer with super().__init__(...) to set up the inherited part, then initializes its own unique attributes:

fueltank.py
class FuelTank(Tank):          # FuelTank is a Tank
    def __init__(self, capacity, grade):
        super().__init__(capacity)   # build the Tank part first
        self.__grade = grade         # then add what's unique to a fuel tank

    def get_grade(self):            # a new method, on top of the inherited ones
        return self.__grade

An instance of the subclass has both sets of behavior — the inherited methods and the new one:

use_subclass.py
f = FuelTank(60, "Jet A")
f.fill(20)                 # inherited from Tank — no code rewritten
print(f.get_level())       # 20    (inherited method)
print(f.get_capacity())    # 60    (inherited method)
print(f.get_grade())       # Jet A (the subclass's own method)
Why super().__init__() matters

The subclass initializer is responsible for setting up the whole object. Calling super().__init__(capacity) runs Tank's setup so the inherited __capacity and __level exist; forget it, and the inherited methods would have no data to work with.

Picturing the hierarchy

Inheritance in a UML diagram

UML shows inheritance with a line carrying an open (hollow) triangular arrowhead that points from each subclass up to its superclass. The subclass boxes list only their new members — the inherited ones aren't repeated, because the arrow already says "everything in Tank is here too."

The arrow direction is a claim

The triangle always points toward the more general class. Read it as "a FuelTank is a Tank" — the same "is a" relationship, now drawn. This is the identical notation you use in the Java and Logic & Design courses.

One call, many forms

Polymorphism

Polymorphism is an object's ability to take different forms — so that the same method call does the right thing for whatever object it lands on. It rests on two ingredients: a method defined in a superclass can be overridden in a subclass (a method with the same name), and Python calls the correct version based on the object's actual type.

Give Tank a __str__, then override it in each subclass. The override here calls the superclass version with super().__str__() and adds to it:

overrides.py
class Tank:
    # ... __init__, fill, get_level, get_capacity as before ...
    def __str__(self):
        return f"{self.get_level()} of {self.get_capacity()} units"

class FuelTank(Tank):
    # ... __init__, get_grade as before ...
    def __str__(self):                         # OVERRIDE
        return super().__str__() + f", {self.__grade} fuel"

class PressurizedTank(Tank):
    def __init__(self, capacity, max_psi):
        super().__init__(capacity)
        self.__max_psi = max_psi
    def get_max_psi(self):
        return self.__max_psi
    def __str__(self):                         # OVERRIDE
        return super().__str__() + f", rated {self.__max_psi} psi"

Now the polymorphism shows itself. Loop over a mixed list of tanks and call the same print on each — every object runs its own __str__:

poly_demo.py
tanks = [FuelTank(60, "Jet A"), PressurizedTank(40, 3000)]

for t in tanks:
    print(t)        # same call — different result per object type
# 0 of 60 units, Jet A fuel
# 0 of 40 units, rated 3000 psi
Extend or replace

An override can call the superclass version and add to it (as above), or ignore it and do something completely different. Either way, the version that runs is decided by the object's actual class — not by the type of the variable holding it.

Checking an object's type

The isinstance function

Polymorphism is flexible, but sometimes a function needs to confirm it actually received the kind of object it expects. The isinstance function answers exactly that: isinstance(object, class) returns True if the object is an instance of that class — or of any subclass of it.

isinstance_demo.py
f = FuelTank(60, "Jet A")

print(isinstance(f, FuelTank))   # True
print(isinstance(f, Tank))       # True  — a FuelTank IS a Tank
print(isinstance(f, PressurizedTank))  # False

Why bother? If a function calls a method the object doesn't have, Python raises an AttributeError. Checking with isinstance first lets the function stay safe when it might be handed the wrong type:

guarded.py
def summarize(item):
    if isinstance(item, Tank):      # any Tank or subclass is welcome
        print(item.get_level(), "units")
    else:
        print("not a tank — skipping")

summarize(FuelTank(60, "Jet A"))   # 0 units
summarize("a string")             # not a tank — skipping
# without the guard, "a string".get_level() would raise AttributeError
Capstone · putting it together

Robust class definitions: raising and handling exceptions

So far fill quietly clamped at capacity — ask for too much and it just stopped, saying nothing. A more robust class refuses invalid input loudly: the method raises an exception, and the main program handles it with try/except. The class enforces its own rules; the caller decides how to react. This separates detection (inside the method) from handling (at the call site).

Step 1 — define exception classes (using inheritance!)

An exception is just an object, so its type is a class — and exception classes form an "is a" hierarchy exactly like the one you built above. Define a base TankError that inherits from Python's built-in Exception, then specialized subclasses:

errors.py
class TankError(Exception):          # a TankError IS an Exception
    """Base class for all tank problems."""

class NegativeAmountError(TankError):  # ... IS a TankError
    pass

class OverfillError(TankError):       # ... IS a TankError
    pass

Step 2 — raise from inside the method

Refactor fill so it checks its input and raises when something is wrong, before changing any data. The object's state is never left corrupted:

robust_tank.py
    def fill(self, amount):
        if amount < 0:
            raise NegativeAmountError(f"amount cannot be negative: {amount}")
        if self.get_level() + amount > self.get_capacity():
            raise OverfillError(f"{amount} would overflow a {self.get_capacity()}-unit tank")
        self.__level = self.__level + amount   # only runs if the input was valid

Step 3 — handle it in the main application

The caller wraps the risky operation in try/except and decides what to do:

main.py
tank = FuelTank(60, "Jet A")

try:
    tank.fill(100)              # asks for too much
except OverfillError as err:
    print("Refused:", err)      # Refused: 100 would overflow a 60-unit tank

print(tank.get_level())         # 0  — the tank was protected

Here is where the inheritance hierarchy pays off again. Because every specific error is a TankError, the caller can catch the whole family with one handler — or catch a specific one when it wants to respond differently:

catch_family.py
try:
    tank.fill(-5)
except TankError as err:       # catches NegativeAmountError AND OverfillError
    print("Tank problem:", err)  # Tank problem: amount cannot be negative: -5
the whole module, in one pattern

Catching TankError also catches its subclasses because NegativeAmountError and OverfillError are TankErrors — the same "is a" relationship that drives inheritance and polymorphism. A robust class raises specific, meaningful exceptions; a well-written caller handles them at the level it chooses.

Review

Check yourself

Predict each answer, then open the card. Even better, try it in the console above.

Q1What does the "is a" relationship mean, and how do you declare it in code?▸

It means one class is a specialized version of another — a FuelTank is a Tank. You declare it by naming the superclass in parentheses: class FuelTank(Tank):. The subclass then inherits the superclass's attributes and methods.

Q2Why does a subclass __init__ usually call super().__init__(...)?▸

To set up the inherited part of the object. The superclass initializer creates the attributes the inherited methods rely on (here __capacity and __level); the subclass then adds its own. Skip it and the inherited methods have no data to work with.

Q3In a UML diagram, which way does the inheritance arrow point, and what kind of arrowhead is it?▸

A line with a hollow (open) triangular arrowhead points from the subclass up to the superclass — toward the more general class. It reads as "subclass is a superclass."

Q4What is polymorphism, and what two things make it work?▸

It's an object's ability to take different forms, so the same call behaves correctly for each type. It needs (1) a method defined in a superclass and overridden (same name) in a subclass, and (2) Python calling the correct version based on the object's actual class.

Q5Given a FuelTank object f, what do isinstance(f, FuelTank) and isinstance(f, Tank) return?▸

Both return True. isinstance is True for the object's own class and for any superclass — because a FuelTank is also a Tank.

Q6In a robust class, where is invalid input detected, and where is it handled?▸

Detected inside the method, which raises an exception when the input breaks a rule. Handled at the call site, where the main program wraps the call in try/except and decides how to respond. The method enforces; the caller reacts.

Q7If NegativeAmountError and OverfillError both inherit from TankError, what does except TankError catch?▸

Both of them. Catching a superclass exception also catches its subclasses, because each specific error is a TankError. That lets one handler cover the whole family, or you can catch a specific subclass to respond differently.

Q8Why raise an exception in fill instead of silently clamping the level at capacity?▸

Clamping hides a problem — the caller never learns the request was invalid. Raising makes the violation explicit and lets the caller decide how to respond, while the object protects its own state by raising before changing any data.

Reference

Key terms

inheritance
Creating an "is a" relationship in which one class is built from another.
"is a" relationship
Exists when one object is a specialized version of another.
superclass (base class)
The general class whose attributes and methods are inherited.
subclass (derived class)
A specialized class that inherits from a superclass and can add its own members.
super()
Used inside a subclass to call the superclass's version of a method, e.g. super().__init__(...).
overriding
Defining a method in a subclass with the same name as one in the superclass.
polymorphism
An object's ability to take different forms, so the same call runs the right version for its type.
isinstance function
isinstance(object, class) — True if the object is an instance of that class or any subclass.
AttributeError
Raised when code calls a method or uses an attribute the object doesn't have.
raise statement
Signals an error by creating and throwing an exception object.
exception
An object representing an error condition; its type is a class.
custom exception class
A user-defined exception, created by inheriting from Exception (or another exception).
try / except
The statement that handles an exception raised by code it surrounds.
detection vs. handling
Detecting an error (raising inside a method) is separate from handling it (catching at the call site).
robust class
A class that validates input and raises meaningful exceptions instead of failing silently.
